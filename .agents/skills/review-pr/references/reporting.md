# GitHub PR 审查报告

完成语义审查和最终刷新后读取。报告使用当前请求语言，优先给出有行动价值的结论。

## 结构与问题身份

保留 P0–P3 优先级与稳定 ID：

- `C`：已有开放评论。
- `F`：独立发现。
- `Q`：需要用户决策的正确性或范围问题。

C/F/Q 只表示来源或类型，数字用于稳定跟踪，不表示发现时间。复审沿用同一问题的 ID；
只有具备准确上轮快照时才比较“已修复、仍存在、新增”。没有时标明本轮确认，
不推断首次发现时间。

报告按以下顺序组织，省略没有内容的可选分区；审查结论、PR 内容介绍和审查范围与验证保留，
简单 PR 可以用短段落表达。

1. **审查结论**：先用一句话说明代码审查建议与主要阻塞项，再简述功能目标满足程度和实现方式
   判断。区分静态证据与真实运行验证；CI 失败/pending、必需验证或最终刷新缺口影响结论时，
   在开头说明。复杂报告可增加按 P0–P3 跨 C/F 排序的简短行动索引。
2. **PR 内容介绍**：在具体问题前解释目的、主要变化及必要的使用与实现背景，按下节组织。
3. **待处理问题**：有效的已有评论在前，独立发现在后，组内按风险排序。两类都有内容时
   使用“待处理的已有评论”和“独立发现”二级分区。
4. **待确认决策**：只放需要用户选择的正确性/范围事项或没有构成缺陷的低风险更优方案，
   给出推荐和主要取舍；关联 C/F 时引用 ID，不重复证据。
5. **旧评论与线程处理记录**：简述无需修改的每个评论，保留原问题、当前代码证据、判断、
   permalink 和实际线程状态。已修复或不适用不等于已 resolve。
6. **审查范围与验证**：记录远程快照、本地准备、实际检查、限制、最终刷新和实际操作。

摘要明确区分代码问题数、待决事项数和最终开放线程数。“已修复但仍开放”仍计入开放数。
多个线程指向同一问题时，每个线程保留链接、状态和判断，但问题数去重。

## PR 内容介绍

面向不熟悉该改动的读者，结合 PR 描述、关联问题和准确 diff 提炼内容；不要照抄 PR 正文、
罗列文件清单或根据代码反向编造需求。来源与目标核对遵循
[问题背景协议](problem-review.md)，缺少背景时标明推断或证据缺口。

- **目的与背景**：说明解决什么问题、为什么需要，关联 issue 有助于理解时附链接。
- **主要变化**：说明合并后用户或开发者可感知的变化；简单修复可用一句修改前后的对比。
- **使用方式**：功能型 PR 按需要说明入口、典型操作和前提；内部重构说明调用方或维护方式
  的变化，不强行编写用户操作步骤。
- **实现思路**：按需要用少量文字串起核心流程和关键模块，为后续问题提供上下文。
- **范围与限制**：有实质影响时说明依赖、未覆盖场景及待验证体验，不臆造限制。

目的与主要变化始终说明，其他内容按实际需要展开；简单修复用短段落，较复杂功能用数段或
简短列表，不机械填满五个字段。区分作者声称支持、代码已有实现与实际验证通过；内容介绍
不能替代缺陷分析或验证结论。复审也保留简短介绍，重点变化可指出，但不整段复制旧报告。

## 排版与分隔

- 每两个相邻主要模块之间统一使用一条 Markdown 分割线 `---`，简单和复杂报告均适用。
- 同一模块中的相邻问题卡片也使用一条 `---`；模块标题与其第一张卡片之间不加分割线。
- 分割线独占一行，前后各留一个空行；模块内部的普通段落、字段和列表不额外分隔。
- 可选模块省略时一起移除多余分割线，不保留空模块、连续分割线或首尾分割线。
- 不依赖 HTML、折叠块、颜色或宽表格。结论、行动索引和正文的 ID 必须一致，旧评论不重新
  包装为新 finding。

## Finding 契约

二级标题用于报告分区，三级标题用于问题，例如 `### [P1] F1 — 简洁标题`。每个有效问题包含：

- 准确快照中的位置。
- 触发条件和用户/系统影响。
- 代码、diff 或调用链证据。
- 最小具体修复。
- 针对性的建议验证。

已有评论以 C 编号和 permalink 标明；独立问题以 F 编号并标明“本轮新增”、
“上轮发现，本轮仍成立”或“本轮确认”。评论判断使用自然语言，如“仍需修复”、
“部分成立”、“已修复”、“不再适用”或“证据不足”，不向用户堆叠内部枚举。

路径使用准确审查快照的链接；旧评论行号标记为原位置，不用旧行号伪造当前 diff 链接。
长 SHA 统一放在验证区。问题内使用短的段内标签；复现步骤用有序列表，多条证据用简短列表。
待执行检查写“建议验证”，与验证区的“已执行”分开。

## 验证区最低信息

简单报告可合并紧密相关项，但失败和限制不得省略。复杂报告可按“范围与快照”、
“本地准备”、“已执行验证与限制”、“刷新与操作”组织。保留：

- 关键验收条件与实现/验证证据的对应及覆盖缺口；目的、主要变化和使用背景已在内容介绍中
  说明，此处不重复整段介绍，必要时引用其对应事项。
- 实现方式评估：当前路径、比较依据、替代方案与代价，或“当前方式已足够”的可复核结论。
- 完整 remote head SHA、frozen base 与 merge-base；latest-base 本地集成快照单列。
- 本地分支/实际 upstream 或 worktree 路径、分支和原 checkout 状态；本人 PR 的同名分支复用、
  collision fallback 与原因（如适用）。本地领先时分别列出 checkout SHA、远程审查 SHA 和
  未纳入审查的本地提交数，说明从冻结 Git 对象取证及本地测试的归属限制。
- latest-base 是否执行、merge/冲突处理和 head/base ancestry 结果。
- 实际检查、结果、未运行项和环境阻塞；CI 状态与代码判断分开。
- 最终刷新的 head、PR `updatedAt`、需求证据与 threads/replies 覆盖，以及新活动的复核结果。
- 线程计数：初始开放、本轮确认 resolve、最终开放；外部新增、关闭或重开时解释差额。
- 实际本地和远程操作，特别是 resolve、提交 review、merge 和 push。“未 push”不等于“未修改 GitHub”。

没有 finding 时明确说明未发现可证实缺陷，不承诺没有 bug，也不将其写成“已验证可合并”。
简单且没有待处理问题时，可参考 [精简报告示例](report-example-simple.md)；复杂复审参考
[复审报告示例](report-example.md)。按需读取一种，不复制示例的占位符、计数或结论。
