# 代码与文档维护

先读项目规则。用户只要求检查、评估或方案时，仅读取和报告。用户要求修改时，按指定任务执行。
只整理 Markdown 时保留代码，只简化代码时保留无关文档的排版。综合维护可以同时检查两者。

## 确定范围

用户指定的文件、目录、提交范围、当前改动或全仓优先。检查「当前改动」时，分别查看已暂存、未暂存和未跟踪文件。
保留用户已有的改动和暂存边界。

未指定范围时，从当前 `HEAD` 可达的历史选取最近 7 天的提交，最多 100 个。以提交选定路径，工作树改动本身不扩大范围。

```bash
git log HEAD --since-as-filter='7 days ago' --max-count=100 --format=%H
```

旧版 Git 不支持该选项时，按相同遍历顺序读取提交者时间，先过滤最近 7 天，再取前 100 个。
尚无提交或窗口为空时，报告近期没有候选。

取选中提交的改动路径并集。普通提交与父提交比较，根提交按新增文件处理，合并提交与第一父提交比较。
沿重命名定位现行路径，并检查已删除文件的引用。文档优先检查现行指南；历史记录和已完成计划默认只作对应版本的证据。

## 清理代码

选择收益明确、可以独立验证的改动。处理局部简化、去重或可读性时，读取[代码简化指南](references/code-simplifier.md)。

- 合并重复规则前，比较调用方的默认值、失败分支和副作用。保留错误传播、重试、取消和恢复语义。
- 文件混合了不同职责时，根据调用方和依赖确定归属。移动前核对构建目标、模块依赖和资源路径。
- 退役代码前，核对公开 API 的外部调用约定、动态注册与反射、序列化与旧数据、配置、CI 脚本和工程文件。无法确认用途时保留，并说明缺少的证据。
- 简化中发现疑似缺陷时，说明触发条件与现有证据。改变可观察行为的修复单独处理；专门查找缺陷或回归时使用 `review`。

涉及对应技术栈的代码维护时，按需读取平台指南：

- [Swift、SwiftUI 与 Xcode](references/swift-xcode.md)
- [Electron、TypeScript、React 与 IPC](references/electron-typescript.md)

## 整理 Markdown

先按主题分段，再处理过长的正文行。沿用项目的行长约定；没有约定时，以每行 80–100 个源码字符为参考。
汉字、字母、标点、空格和 Markdown 标记中的每个字符都计一。短段落可以更短，不为凑足 80 字符而拼接。

- 参考上限内能写清的句子或列表项保持一行。超长时在靠近上限的句末或分句标点后换行，保留词语完整，避免续行只剩几个字。
- 保留 YAML frontmatter、标题、表格、代码块、行内代码、链接目标，以及 HTML 块、标签和注释。独立长 URL 可以超过参考上限。
- 保留列表续行缩进、引用层级、GitHub 提示块的标记和前缀，以及有意的硬换行。按原文编辑，保留措辞、事实和先后关系。
- 比较排版前后的渲染结构、正文、命令、链接和标题锚点。抽查原本较短的列表项和调整后的长段落。

## 核对代码与文档

从候选代码查找描述其行为的现行文档，也从候选文档反查实际入口。核对用户会依赖的参数、默认值、重试条件和资源路径。
文档承诺列出全部支持项时，与实际注册表或入口逐项比对，包括各语言版本；精选示例按其声明的范围判断。

只报告同一版本、构建配置和功能开关下，由实现、配置或可复现结果证实的矛盾或漏项。
已有差异默认提示用户；若证据只表明两者冲突，说明哪一侧应调整仍需决定。本轮改动使文档过时时，在授权范围内同步并复核。

## 验证与交付

按项目规则验证和交付。纯排版改动检查 Markdown；代码改动验证受影响的正常入口、公开接口、兼容性和失败路径。
报告检查范围、改动及验证结果。环境受限时写明哪些入口已验证、哪些未能运行。

即使零改动，也要提示已证实的文档差异，给出文档和实现的位置、具体差异、使用者受到的影响和处理状态。
