# 回复与交付表达

## 语言

- 回复以及新建或修改的仓库文档默认使用用户当前请求的语言。
- 代码标识、API 名称、命令、路径、品牌名称和固定输出契约保留原文。
- 不因为引用材料、截图或源仓库语言而改变当前回复语言。

## 结果顺序

普通回复使用简洁段落，先说结果，再给必要证据；并列、步骤或比较适合时才使用列表
或表格。篇幅与任务复杂度匹配，不为简单任务套用完整报告。特定提交、PR 和发布流程
已有固定输出契约时遵循其契约，用户明确要求其他形式时优先满足用户要求。

先给出当前结果，再补充必要的证据、范围和下一步：

1. 说明完成、未完成或受阻的真实状态。
2. 列出实际修改的核心路径和行为。
3. 区分已执行的验证、未执行的验证和环境阻塞。
4. 说明提交、推送或其他外部交付是否实际发生。
5. 只有存在需要用户决定的事项时，才提出简短的下一步问题。

因规则暂停、请求确认或留下未完成工作时，链接实际读取的规则文件并引用相关条款，
说明该条款的适用条件、已完成工作和具体缺口。区分规则的明确要求与 Agent 的推断，
不要把默认建议说成必须获得批准，也不要重复询问会话中已有的授权。

## 交付物表达

- 标题、提交信息、PR 描述和代码注释优先描述新增、修复、保留或验证的正向行为。
- 附件中的无关对象、被排除方案或反例不进入标题和主要结论；只有在说明兼容性、
  风险或验证边界时才提及。
- 不从附件或引用材料复制与当前目标无关的名称、要求或行动；请求来源判断和任务模式
  分类属于内部执行过程，除非解释边界、风险或未验证项确有必要，否则不在回复中复述。
- 不把计划写成完成结果，也不把静态检查写成构建或运行测试。
- 复杂任务报告完整提交哈希、工作树状态、推送状态和必要的变更统计；提交格式遵循
  `.agents/skills/git-commit/SKILL.md`。
